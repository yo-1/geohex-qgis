### L01・L02・L03・L04・L05・L06・L07・L09・L10 実施記録（2026-10-03）

- 検証環境: QGIS 3.44.13-Solothurn（`qgisMinimumVersion=3.40` を満たす）、Windows
- 対象レイヤ: 業務で使用している道路台帳由来のラインレイヤ（約6万フィーチャ、全パートがライン。ポリゴン・対象外パートは0件）
- L01（Level 5）: 正常終了。16セル出力（5.7秒）。ログに `入力: フィーチャ 60264 件 → 対象パート ポリゴン 0 / ライン 60287（対象外パート 0）` が表示され、エラー・警告なし。
- L02（Level 6）: 正常終了。84セル出力（5.9秒）。同上ログ形式を確認。
- L03（Level 7）: 正常終了。620セル出力（6.47秒）。同上ログ形式を確認。Level5→6→7→8のセル数（16→84→620→4,938）の増加倍率が5.25倍→7.38倍→7.96倍と、理論値（1レベルあたり約9倍）に漸近する傾向を確認。
- L04（セル中心が陸域内モード指定）: Level 6・Level 10の双方で実行。期待通り警告
  `ライン入力には『中心が陸域内』は適用できないため、『重なるセル』で処理しました。` が表示された。
  さらに、出力セル数が同一レベルの『重なるセル』指定時と完全一致することを確認（Level 6: 84セル、Level 10: 239,186セル、いずれも一致）。警告表示だけでなく、実際の処理結果が仕様通り『重なるセル』として扱われていることまで確認できた。
- L05（出力属性 `area_m2` の検証、対象: Level 7実行結果・620セル）:
  1. 初回、「ジオメトリ属性を追加」ツールを `計算方法 = レイヤのCRSでデカルト座標計算`（レイヤCRS=EPSG:4326）で実行したところ、`area` 列が平方度単位（`area_m2` との比が約1.0×10¹⁰のオーダー）となり比較不可と判断。
  2. 次に `プロジェクトのCRSでデカルト座標計算` を試したが、プロジェクトCRSも地理座標系であったため同様に平方度単位のままであることを `area_m2/area ≈ 111320² × cos(緯度)` の関係から確認。
  3. `楕円体を用いた計算`（METHOD:2、楕円体=WGS84 (EPSG:7030)、Project Properties → 全般 → 計測で確認済み）に切り替えたところ、単位はm²相当になったが `area_m2` に対して常に約23%大きい値となった（比1.230〜1.232、サンプルした緯度範囲35.3〜35.6°では緯度依存の変化は見られず）。原因はプロジェクトの楕円体設定の誤りではないことを確認済みだが、根本原因は本検証では特定できていない（QGIS Processingツール側の当該計算方式の実装挙動として、未確認事項のまま記録する）。
  4. 上記(3)に依存しない独立したクロスチェックとして、出力レイヤをEPSG:2451（平面直角座標系9系、対象エリアを含む）へ再投影し、`レイヤのCRSでデカルト座標計算`（投影後は平面direct計算）で面積を再計算。結果、`area_m2` との差は約0.018%（例: 789,665.36 vs 789,522.68 m²）に収束し、良好に一致することを確認。この差はEPSG:2451の投影歪み（本セルサイズ・対象エリアでは無視できる水準）として説明可能な範囲。
  - **結論**: `area_m2` の算出ロジック（`algorithm.py` の `QgsDistanceArea.measureArea`、楕円体=WGS84）は妥当と判断し、L05をPASSとする。ただし(3)の「楕円体を用いた計算」処理ツールとの約23%の乖離は原因未特定のまま残る（`area_m2` 自体の正しさとは別の、QGIS標準ツール側の検証手法に関する留意事項）。
- L06: 上記いずれの実行でも `入力: フィーチャ○件 → 対象パート ポリゴン○ / ライン○（対象外パート○）` 形式のログ出力を確認。
- L07（出力0件になる入力での警告確認）:
  - 当初、既存ラインレイヤに対して「選択した地物のみ」をONにした上で選択を0件に戻す方法を試みたが、QGISの仕様上、選択地物数が0になると「選択した地物のみ」チェックボックス自体が自動的にOFFへ戻ってしまい、この方法では入力を空にできないことが判明。
  - 代替として、ジオメトリ型「ラインストリング」・地物数0件の一時スクラッチレイヤ（レイヤ→レイヤを作成→一時スクラッチレイヤを作成、CRS: EPSG:4979）を作成し、これを対象範囲レイヤとして指定して実行（「選択した地物のみ」はOFF）。
  - 結果: ログに `入力: フィーチャ 0件 → 対象パート ポリゴン 0 / ライン 0(対象外パート 0)` に続けて、期待通り `出力が0件です。入力が空（『選択地物のみ』で選択が0件の場合を含む）、対象外のジオメトリ、座標変換の失敗などを確認してください。` の警告が表示され、クラッシュ等なく `完了: 0 セル出力（0.0 秒）` で正常終了。
- L09（複数パート・分岐/交差を含むラインレイヤでの重複セル排除確認、対象: L03と同じLevel 7実行結果・620セル）:
  - 対象レイヤは分岐・交差を多数含む実務道路台帳由来のラインレイヤ（約6万フィーチャ）であり、L09が要求する条件を満たす。
  - 出力された `GeoHexセル` レイヤに対し、メニュー「ベクタ」→「解析ツール」→「基本統計量」（対象フィールド: `code`）を実行。
  - 結果: `COUNT: 620`、`UNIQUE: 620` と完全一致（`EMPTY: 0`）。重複するcodeは存在せず、複数パート・複数フィーチャにまたがって生成されたセルが重複出力されていないことを確認。
- L10（自己交差ラインでのクラッシュ安全性確認）:
  - 一時スクラッチレイヤ（ラインストリング）上で、自分自身と交差する形状（X字形）の線を1本手描きして実行。
  - 結果: ログに `入力: フィーチャ 1件 → 対象パート ポリゴン 0 / ライン 1(対象外パート 0)` に続けて `完了: 1 セル出力（0.0秒）` が表示され、クラッシュせず正常終了。「○件のフィーチャで無効なジオメトリを自動修復しました」等の自動修復メッセージも表示されず、ラインジオメトリが（ポリゴンと異なり）自動修復の対象外のまま処理されていることを確認。
- 参考（チェックリスト対象外、追加確認）: 同レイヤでLevel 8（4,938セル、11.5秒）、Level 10（239,186セル、44.1秒）も正常終了を確認。
- 備考: 検証環境に同居する別プラグイン（hxmlimport）由来のPython例外がログパネルに表示されたが、GeoHex Generatorの実行ログにはエラー・警告は一切出ておらず、本プラグインとは無関係。

## H05・H06: 公式GeoHex v3.2 JSとの比較（結果報告）

既存チェックリスト9章「H: GeoHex互換性」のH05・H06について、以下のとおり実施済み。

| ID | 検証 | 結果 |
|---|---|---|
| H05 | GeoHex v3.2公式JSとの比較 | ☑ 一致（920件、不一致0件） |
| H06 | 複数地点・複数Levelで公式JS比較 | ☑ 実施済み |

**手順**（再現可能な形で記録）:
1. `http://geohex.net/src/script/hex_v3.2_core.js` から公式JSソースを取得。
2. Node.js の `vm.runInThisContext` でこのファイルをグローバルスコープで実行し、`GEOHEX.getZoneByLocation` / `getZoneByCode` / `getHexCoords` をそのまま呼び出す（アルゴリズムを読み替えず、公式コードの実行結果そのものを使用）。
3. 固定代表点（日本国内の主要都市・最南端/最北端、世界の主要都市、日付変更線付近、極付近、計20地点）× Level 0, 3, 7, 9, 11, 15、および日本域・世界域の疑似乱数点（各300点、Level 0〜15）の合計920件で、公式JSの出力（`code`, `x`, `y`, 中心緯度経度, `getHexCoords`の6頂点, decode結果）を生成。
4. 本リポジトリの `geohex_generator/geohex_v3.py`（Pythonポート）で同じ入力を処理し、全項目を数値許容誤差 `1e-9`（度）で比較。
5. **結果: 920件すべて一致（不一致0件）。**

このうち代表的な24地点・Levelの組み合わせを `tests/test_geohex_v3.py` の `OfficialJSCrossValidationTest` に固定の期待値として埋め込み、Node.js非依存の回帰テストとして恒久化した（PR化予定）。全920件を再生成するスクリプト自体はリポジトリに含めていないため、再度フルセットでの確認が必要な場合は、上記手順を再実行すればよい。
