# GeoHex 利用ガイド：性質・利点と欠点・ユースケース

調査日: 2026-09-20 ／ 対象: GeoHex v3.2（本プラグインの実装対象）

この文書は、GeoHex を「いつ使うと有利か／使うべきでないか」を判断するための資料です。
記述には根拠の強さを付けています。

| 記号 | 意味 |
|---|---|
| **[出典]** | 公開されている資料で確認した内容（出典を末尾に記載） |
| **[検証]** | 本プロジェクトの実装・テストで確認した内容 |
| **[提案]** | 調査をもとにした提案。**効果は未検証** |

性能や使い勝手の向上について、GeoHex 自体を計測した公開データは見つかっていません。
「向上が期待できる」と書いてある箇所は、六角形グリッド一般の知見に基づく仮説です。

## 1. GeoHex の性質

- Web メルカトル平面上の**正六角形**で世界を隙間なく敷き詰める。上下の辺が水平。**[検証]**
- レベル 0〜15。コード長は「レベル＋2」文字。レベルが1つ上がると長さは 1/3、面積は 1/9。**[検証]**
- 点 → セルは式だけで決まる。データやテーブルの参照は不要。**[検証]**（1点あたり約 7 µs、Python 単一スレッド、開発用サンドボックスでの実測。環境依存）
- 最新版は V3.2。コアの JavaScript が公開されており、ライセンスは MIT（© 2009 @sa2da）。**[出典]**
- 多くの言語に移植されている（Perl, Ruby, Java, PHP, Swift, Python など）。**[出典]**

### 「円に近い」とは何か

六角形は、隙間なく敷き詰められる図形（正三角形・正方形・正六角形）の中で、最も円に近い。

| 指標 | 正六角形 | 正方形 |
|---|---:|---:|
| 円らしさ（4πA/P², 円=1） | 0.907 | 0.785 |
| 隣接セルの中心間距離 | 6方向すべて等しい | 辺方向1 : 対角方向 1.414 |

**[検証]**（計算値）。ArcGIS の解説も、六角形は周長÷面積の比が小さく、エッジ効果によるサンプリングバイアスが小さいこと、隣接セルまでの距離が均等なことを挙げている。**[出典]**

GeoHex は Web メルカトル平面上の正六角形なので、**地上でもほぼ正六角形**に保たれる。ただし、Web メルカトルは球の式を楕円体の緯度に当てはめているため、厳密な等角ではない。日本の範囲では、縦（南北）が横（東西）より約0.3〜0.6%短くなる。**[検証]**（計算値）
主に変わるのは**大きさ**である（次節）。

## 2. 利点と欠点

### 利点

| 利点 | 内容 |
|---|---|
| 隣接関係が単純 | 隣は常に6つで、距離が等しい。近傍集計・ホットスポット分析・「Nセル圏」の定義が簡単 **[出典][検証]** |
| 円に近い | 正方形メッシュより、エッジ効果・方向の偏りが小さい（一般論）**[出典]** |
| 五角形がない | 平面格子なので、H3 のような五角形セルは存在しない **[検証]**（H3 に12個の五角形があることは **[出典]**） |
| 短いコードで精度を選べる | 1点を2〜17文字で表し、文字数を減らすと粗い位置になる。位置のぼかし（プライバシー保護）に使える **[出典]** |
| 文字列キーで扱える | キー・バリューストアや DB の文字列列にそのまま入る。位置の集計が `GROUP BY` になる **[出典]** |
| 実装が軽く、権利が緩い | 公式コアは MIT。純Pythonで約300行（コメント含む）、依存ライブラリなし **[検証]** |

### 欠点

| 欠点 | 内容 |
|---|---|
| **面積が均等でない** | 地上の面積は約 cos²(緯度) 倍。北緯 24°と 45.5°の比で約1.70倍。JIS 地域メッシュは度で区切るので約 cos(緯度) 倍で、同じ範囲で約1.30倍 **[検証]**（計算値）。密度の比較には面積補正が必要 |
| 厳密な入れ子ではない | 子セルは親セルの境界をまたぐ。コードの前方一致で集計すると、親の六角形ではなく「中心＋隣接6＋左右2」の9セルの塊（横長）になる **[検証]** |
| レベルの刻みが粗い | 1レベルで面積が 9 倍。中間の大きさは選べない **[検証]** |
| 適用範囲 | メルカトルの限界（約 ±85.05°）内。日付変更線付近は特別扱いがあり、実装ごとの差が出やすい **[出典]** |
| 標準・公式統計との接続がない | 官庁統計は JIS 地域メッシュで提供される。GeoHex 単位の公的統計は見つかっていない **[出典]** |
| エコシステムが小さい | 主要なクラウド DB の解説（BigQuery）は、S2 と H3 を扱い、GeoHex は登場しない **[出典]**。移植ライブラリには更新が止まったものが多い（例: uupaa の npm 版は最終公開が7年前、Scala 版の最新リリースは2021年）**[出典]** |
| 版・実装の混在 | V1/V2/V3 でレベルの定義が違う（V2 は25レベルで長さが 1/2 ずつ）。記事によっては古い版の数値を載せている **[出典]** |

**H3 との違い**: H3 にも面積の変動はある（Esri の解説によれば、解像度3のセルの地上面積は場所により約2,300〜5,800平方マイルの範囲で変わる）**[出典]**。一方、GeoHex はメルカトル平面上で大きさが一定なので、地上面積は緯度で単調に変わる（日本の範囲で約1.7倍、緯度85°付近ではさらに極端）。H3 には五角形セルが12個あるが、GeoHex にはない。**[出典][検証]**

## 4. 新しい用途の提案 [提案・未検証]

GeoHex が有利になりやすいのは、次の条件に当てはまる場面です。
(a) 近傍・隣接の扱いが重要、(b) 方向による偏りを避けたい、(c) 短い文字列のキーで集計したい、(d) 位置をぼかして共有したい。

| 提案 | 内容 | 注意 |
|---|---|---|
| 位置情報の粗視化共有 | 人流・混雑・利用状況を、レベルを選んでコード単位で公開する。少数のセルは、上位レベルへまとめて秘匿する | 「上位レベルへまとめる」ときは9セルの塊になる（前節）。個人特定のリスク評価は別途必要 |
| 近傍を使う分析 | ホットスポット分析、空間自己相関、密度の平滑化。隣接の定義が単純になる | 密度は面積補正（本プラグインの `area_m2`）が必要 |
| サービス圏・到達圏の近似 | 「N セル圏」を、方向によらない距離の目安に使う（避難所、施設、基地局） | 実際の到達圏は道路・地形で決まる。近似であることを明示する |
| 道路・線状施設の密度評価 | 路網などを六角形ごとに集計する（延長÷セル面積）。方向の偏りを抑えて比較できる | 面積補正が必須。セルは丸ごと出力されるため、切り出しが必要なら「交差」を使う |
| 災害時の被害報告の集計 | 報告位置をコードに変換して、リアルタイムに集計する | 通信途絶時の運用や、報告位置の精度を別途検討する |
| データカタログの位置検索 | CKAN などのメタデータに GeoHex コードを付与し、粗い位置での検索・絞り込み用のキーにする | 前方一致検索は9セルの塊になる。矩形範囲との併用が現実的 |
| 位置履歴の圧縮 | 経路を座標列ではなくコード列で保存する（考案者の資料が挙げるデータ量削減） | 復元できるのはセル中心まで |
| 分散データストアのキー | 位置に基づくシャーディングやキャッシュのキー | 隣接セルへの分散に注意 |

## 5. これまでのメッシュとの置き換え評価 [提案・未検証を含む]

| 分野 | 現在よく使われるもの | GeoHex で期待できること | 向かない点・注意 | 判断 |
|---|---|---|---|---|
| 公的統計（人口・経済など） | JIS 地域メッシュ | ほぼなし | 統計はメッシュコードで提供される。面積の均等性も JIS メッシュのほうが高い（日本の範囲で 1.30 倍 対 1.70 倍） | **置き換えない**。併用でコードを両方持つ |
| 人流・混雑の可視化 | 数百メートル四方の正方形メッシュ **[出典]** | 円に近く、隣接との比較が単純 | 既存の集計基盤の変更コスト | **可視化・近傍分析に向く** |
| 店舗・拠点の商圏分析 | 正方形メッシュ、行政区 | 距離帯・近傍検索が単純 | 面積補正が必要 | 向く（補正前提）|
| タクシー・配送の需要エリア | 正方形メッシュ **[出典]** | 隣接セルへの需給調整が単純 | H3 が使える環境なら H3 も有力 | 用途次第 |
| 防災・避難 | メッシュ、行政区 | 圏域の近似が単純 | 実際の到達は地形・道路で決まる | 補助的に向く |
| 位置情報の匿名化 | メッシュ、行政区 | 精度を文字数で選べる | 個人特定リスクの評価は別 | 向く |
| 世界規模・高緯度の分析 | S2、H3 | ― | メルカトルの限界と、緯度による面積差の急増 | 向かない |

**性能について**: 点→セルの変換が式だけで済み、空間結合が不要になる点は、集計の高速化に寄与する可能性がある。
ただし、GeoHex について計測した公開データはなく、USERDIVE の発表資料は、文字列切り詰めによる集計でインデックスが効かず遅かったという課題を報告している。**必ず自環境で計測すること。**

## 6. 平面直角座標系の上に重ねる場合

日本の測量・公共事業では、平面直角座標系（JGD2011、EPSG:6669〜6687 など）の上に六角形メッシュを重ねたい場合がある。

| 方法 | 見え方 | 向くとき |
|---|---|---|
| **平面直角座標系の上に直接、六角形格子を作る**（QGIS 標準の「グリッドを作成」の六角形など） | 辺の長さを 100 m・500 m のように指定でき、座標軸に揃う。面積は、平面直角座標系の縮尺係数（中央子午線で0.9999、系の端で1.0001前後に収まるよう設計されているとされる。数値は出典未確認）の範囲でほぼ一定 | 測量・設計で、面積の均一さと切りのよい寸法が必要なとき |
| **GeoHex のセルを平面直角座標系に投影して重ねる** | 大きさは緯度で変わり、切りのよい寸法にならない。回転は、子午線収差の分だけ（下の例で 0.4〜1°程度） | 他システムと共通のセル ID を使いたいとき |
| **H3 のセルを平面直角座標系に投影して重ねる** | 二十面体の面ごとに向きが異なり、座標軸に揃わない。五角形が含まれる場所がある | 同上（面積の変動は GeoHex より小さい傾向だが、日本の範囲での幅は未確認） |

GeoHex のセルを地上で測ったときの大きさ（レベル7、楕円体上の計算値）**[検証]**:

| 緯度 | 幅（東西） | 高さ（南北） | 面積 |
|---:|---:|---:|---:|
| 24° | 約 1,241 m | 約 1,068 m | 約 0.99 km² |
| 35° | 約 1,113 m | 約 960 m | 約 0.80 km² |
| 45.5° | 約 953 m | 約 823 m | 約 0.59 km² |

子午線収差の例（系IXの中央子午線 139°50′に対して）: 経度139.0°・緯度35.4°で約 -0.5°、経度140.6°・同緯度で約 +0.4°、経度141.3°・緯度45°で約 +1.0°。**[検証]**（近似式 Δλ·sinφ による）

**判断の目安**
- 座標のきりのよい、等面積の六角形が要るなら、**平面直角座標系の上で直接作る**。GeoHex・H3 は不要。
- ただし、平面直角座標系は19の系に分かれる。系をまたぐ地域では、系ごとの格子が継ぎ目で合わない。GeoHex や H3 は、全域で1つの格子なので、系をまたいでも同じセル ID になる。
- 両立したいなら、平面上の格子を使い、各セルの中心点から GeoHex（または H3）のコードを属性として付ける。
- 平面直角座標系の座標（JGD2011）から GeoHex のコードを求めるときは、いったん緯度経度（EPSG:6668）に変換する。JGD2011 と WGS84 の差は、この用途のセルの大きさに比べて十分小さい。旧測地系（日本測地系）のデータは、先に変換する。

| 福岡 | 33.59° | 7.46 | 0.828 | 約 565 | 約 489 |

| 仙台 | 38.27° | 6.63 | 0.737 | 約 533 | 約 461 |
| 札幌 | 43.06° | 5.75 | 0.639 | 約 496 | 約 430 |
| 最北端 宗谷岬 | 45.52° | 5.29 | 0.588 | 約 476 | 約 412 |

- 最南端と最北端の面積比は約 **1.78**（どのレベルでも同じ）。JIS 地域メッシュ（3次）は約 1.33。
- 1つのセルの中で、中心から6つの角までの距離の差は約0.4%以内（東西と南北の縮尺差による）。

**H3 の平均値**（解像度ごとの平均面積 = 地球の表面積 ÷ セル数 (2 + 120·7^解像度) で求めた。解像度5の252.9 km²は Esri の解説と一致）

| 解像度 | 平均面積 | 同面積の正六角形の辺（＝外接円半径） | 同 中心→辺の中点 |
|---:|---:|---:|---:|
| 6 | 36.13 km² | 約 3,729 m | 約 3,229 m |
| 7 | 5.16 km² | 約 1,409 m | 約 1,221 m |
| 8 | 0.737 km² | 約 533 m | 約 461 m |
| 9 | 0.105 km² | 約 201 m | 約 174 m |

- 大きさが近い組み合わせは、**GeoHex レベル7（0.59〜1.05 km²）と H3 解像度8（平均 0.74 km²）**。GeoHex レベル6は H3 解像度7（平均 5.2 km²）より大きく、レベル8は解像度9より小さい。
- **H3 の公式表の「辺長」は、辺の長さとして GeoHex と比べない**。解像度5の平均辺長（Esri の解説は「半径 約8.5 km」）は、同面積の正六角形の**中心→辺の中点**（8.54 km）に一致し、辺（9.87 km）とは一致しない。定義は未確認。
- **H3 の地点別の面積・辺長・中心から角への距離は、未計算**。同じ解像度でも、H3 のセルの面積は場所により変わる（Esri）。`tools/compare_grids.py` で計算できる（要 `pip install h3`）。

## 8. 利用時の注意

1. **面積補正**: 密度・比率の比較には、セルごとの面積（`area_m2`）で割る。
2. **前方一致の集計**: 上位レベルの六角形とは一致しない（9セルの塊）。上位レベルの六角形で集計したいときは、座標から上位レベルのコードを計算し直す。
3. **レベル番号は版・実装で異なる**: 他の資料の「レベル」の数値をそのまま使わない。本プラグインは V3.2（レベル 0〜15）。
4. **標準との併用**: 公的統計との突合が必要なら、JIS 地域メッシュのコードも属性として持つ。
5. **表示**: EPSG:3857 で表示すると正六角形に見える。EPSG:4326 では縦に潰れて見える。
6. **帰属表示**: GeoHex は MIT ライセンス（© 2009 @sa2da, http://www.geohex.org）。組み込む製品にも著作権表示を残す。
